# سجل التحقق الحي لموديولات ZS ERP

هذا السجل **ليس ملف ميزات ولا شهادة جاهزية**. نقطة الدخول لتبعيات الكود هي [الخريطة الرئيسية](../../SYSTEM_BLUEPRINT.md)، وفهرس وصف الوظائف هو [SYSTEM_CAPABILITIES.md](../../SYSTEM_CAPABILITIES.md)، والسجل التاريخي للقرارات والاختبارات السابقة هو [REVIEW_ROADMAP.md](../../REVIEW_ROADMAP.md).

## المصدر والحدود

- [module-review-status.json](module-review-status.json) هو سجل machine-readable يضم موديولات `backend/src/modules` الـ37 ومالك توثيق كل موديول. صُفّرت حالة التحقق الحالية مبدئياً لعدم إعادة اختبارات النظام في جلسة إعداد الخريطة، **وليس إنكاراً للمراجعات السابقة**.
- `baseline_code_commit` مرجع لاكتشاف التغييرات بعد إنشاء السجل، **وليس commit جرت عليه اختبارات جديدة**. عند كل مراجعة اقرأ أحدث HEAD وأوضاع التشغيل المستهدفة.
- وصف «مُكتمل 100%» في ملفات القدرات وصف تاريخي، وليس بديلاً عن النتائج المسجلة وتاريخها ونطاقها.

## معنى الحالة

| `state` | المعنى |
| --- | --- |
| `unverified_current_head` | لا يوجد في هذا السجل دليل تحقق قابل للتدقيق يغطي نسخة الكود الحالية؛ قد توجد مراجعة قديمة مفيدة |
| `verified_scoped` | دليل اختبارات/مراجعة مرتبط بـcommit ومحدود بالسيناريوهات والمسارات المسجلة؛ لا يعمم على الموديول كله |
| `release_blocked` | توجد موانع إصدار موثقة حتى لو كانت بعض المسارات صحيحة أو مختبرة |
| `release_ready` | **لا يُستخدم** إلا بتوثيق اختبارات الكود والمال/المخزون والتكامل/القبول الميداني والمتطلبات التشريعية المطلوبة لوضع التشغيل والسوق، مع عدم وجود موانع إصدار مفتوحة |

### شروط الترقية

أي حالة `verified_scoped` أو `release_ready` تتطلب `last_verified_commit` حقيقيّاً من 40 حرفاً، و`verified_at`، و`verified_scope` محدداً بأوضاع التشغيل والعمليات/البلدان إن لزم، و`test_evidence` يتضمن **ما شُغّل بالفعل ونتيجته**. إذا كانت التجربة يدوية، وثّق خطواتها وبيئتها. أي `release_ready` يشترط أن تكون `blockers` فارغة وأن تكون الأدلة كافية لبيئة الإصدار.

يمكن وضع `release_blocked` دون اختبارات جديدة عندما توجد موانع مثبتة بمراجع محددة في `blocker_sources`؛ **لا تستنتج حالة سلامة باقي المسارات** من ذلك.

## إجراء مراجعة أي موديول

1. اقرأ [AGENTS](../../AGENTS.md) والدستور، ثم [SYSTEM_BLUEPRINT](../../SYSTEM_BLUEPRINT.md)، ثم ملف المجال المالك وفق [الفهرس](../../SYSTEM_CAPABILITIES.md).
2. احصل على أحدث SHA من الفرع المطلوب وحدد تشغيل `CLOUD_SAAS` أو `SELF_CONTAINED` أو `LOCAL_PILOT`، والقطاع والبلد والباقة.
3. افحص `git diff <last_verified_commit>..HEAD` عندما يوجد تحقق سابق، **مع توسيع النطاق إلى Core والمستهلكين ذوي الصلة**. واستخدم `node scripts/report-system-map-drift.mjs` كمساعد لإظهار تغييرات الكود منذ خط أساس السجل، لا كبديل عن القراءة.
4. املأ [نموذج تتبع العملية](WORKFLOW_TRACE_TEMPLATE.md) لكل مسار مالي/مخزني/أمني جوهري. صرّح بالمسارات التي لم تراجعها.
5. وثّق اختبارات unit وPostgreSQL integration وواجهات UI والتغليف/الأوفلاين وUAT والقواعد القانونية **كلّاً على حدة**؛ عدم التشغيل يُكتب صراحة. أي Test مُضاف ولم يُشغّل **ليس ناجحاً**.
6. حدّث ملف المجال عند تعديل قدرة. حدّث `SYSTEM_BLUEPRINT.md` عند تغيّر تبعية. حدّث سجل الحالة بعد دليل تحقق فقط، ولا تغيّر `baseline_code_commit` لغرض إخفاء drift.
7. نفّذ `node scripts/validate-capabilities-docs.mjs` للتحقق من الترابط الهيكلي. لو ظهر اختلاف ثقة/واقع، عالجه في المصدر وليس بتغيير اسم الحالة وحسب.

## مثال عملي: HR

حالة HR `release_blocked` حاليًا مبنية على [سجل المراجعة](../../REVIEW_ROADMAP.md) و[مصفوفة إصدار الرواتب القانونية](../../HR_PAYROLL_STATUTORY_RELEASE_MATRIX.md). لا يعني دمج إصلاحات الموظفين والرواتب اعتماد المعادلات الرسمية لجميع الدول أو قبول WPS أو اكتمال UAT. استكمال تلك الأدلة شرط ترقية الحالة.

## منع التداخل بين المحاضر

**الخريطة**: ملكية محركات/جداول وتبعيات وتدفقات. **فهرس القدرات**: روابط المالك. **ملف قدرة المجال**: السلوك المنفذ وحدوده. **السجل الحي**: آخر ثقة مؤرخة وحدودها وموانع الإصدار. **Roadmap**: مراجعات تاريخية والتزامات مفتوحة. **الدستور**: المسموح والممنوع. عند اختلاف أي ملف مع الكود أو الأثر المحاسبي، سجّل التعارض ولا تعتبر الوصف حقيقة تشغيلية.
