# دليل اختبارات الحمل والإجهاد (Load & Stress Testing with k6)

> **الغرض:** توفير منظومة اختبارات أداء وحمل مؤسسية دقيقة تحاكي أقصى ضغوط التشغيل الواقعية على سيرفر المنظومة (Oracle Cloud VPS) وقاعدة بيانات PostgreSQL، والتحقق الحاسم من ثبات النظام، وسرعة الاستجابة، وخلو العمليات المتزامنة تماماً من الاستعصاء القفلي (Deadlocks - SQLSTATE 40P01).

## 1. الثوابت المعمارية المحروسة في اختبارات الحمل

| # | الثابت المعماري | الهدف من اختبار الحمل | السيناريو المقابل |
|---|---|---|---|
| **1** | **PERF-2 & PERF-9** (`PERFORMANCE_CONSTITUTION.md`) | حماية زمن استجابة مزامنة كتالوج الكاشير ($p95 < 150ms$ لفحص النسخة، $p95 < 600ms$ للكتالوج الشامل)، ومنع أي حلقة O(N×M) أو تجميد للخادم عند تزامن عشرات الكاشيرات | `pos-catalog-sync.js` |
| **2** | **الترتيب القانوني للأقفال (§2.1)** (`ARCHITECTURE_INVARIANTS.md`) | حظر استعصاء ABBA والـ Deadlocks نهائياً؛ قفل `products` تصاعدياً قبل `product_location_stock` عند تزامن عشرات طلبات الشراء الإلكتروني على نفس الأصناف | `storefront-checkout.js` |
| **3** | **عزل حدود محاولات الدخول (O72)** | التأكد من أن الهجمات وحزم محاولات تسجيل الدخول المتلاحقة يتم حجبها بـ HTTP 429 دون التأثير على المستخدمين الشرعيين أو مشاركة الدلو بالخطأ | `auth-login-burst.js` |
| **4** | **الإجهاد الشامل للمنصة (Full Stress)** | محاكاة يوم تشغيلي كامل يجمع بين الكاشيرات والمتسوقين ومسابير الصحة معاً للتأكد من توازن الاستهلاك | `stress-all.js` |
| **5** | **مسار الفاتورة الكامل** — §2.1 (applyStockDelta) + القيد المزدوج + صف الوردية | إصدار فواتير حقيقية تحت الحمل: خصم مخزون، وترحيل قيد، وتحديث `cashier_shifts`. ومجموعة منفصلة تبيع **نفس الصنف** من كل المستخدمين لكشف خرق ترتيب الأقفال | `pos-sell.js` |

## 2. هيكل مجلد اختبارات الحمل (`load-tests/`)

```
load-tests/
├── config.js                       # الإعدادات المشتركة، المتغيرات، ودوال توليد البيانات
├── runner.cjs                      # مشغل اختبارات الحمل عبر Node.js
├── run.bat                         # سكريبت تشغيل سريع لبيئة ويندوز
├── run.sh                          # سكريبت تشغيل سريع لبيئة لينكس وماك والسيرفر
└── scenarios/
    ├── pos-catalog-sync.js         # شاشات كاشير مفتوحة تسأل عن نسخة الكتالوج — **قراءة فقط، لا بيع**
    ├── storefront-checkout.js      # مشترون يُنشئون طلبات متجر متزامنة ثم يلغونها — **مسار الكتابة الوحيد**
    ├── auth-login-burst.js         # هجوم تخمين بكلمة مرور خاطئة من عنوان واحد (اختبار الحدّ)
    ├── stress-all.js               # الثلاثة معاً + مسبار صحة (ليس «كل قطاعات النظام» — انظر §6-ج)
    └── pos-sell.js                 # **كاشيرات تبيع فعلاً**: فواتير وقيود ومخزون وورديات (§7)
```

## 3. متطلبات وطرق التشغيل

لا تتطلب المنظومة أي تعديل على كود الإنتاج. يمكن تشغيل الاختبارات بطريقتين:

### الطريقة الأولى: عبر أداة k6 المثبتة محلياً (الموصى بها للمطورين)

1. **تثبيت k6:**
   - **ويندوز (عبر winget أو Chocolatey):**
     ```powershell
     winget install k6 --source winget
     # أو
     choco install k6
     ```
   - **لينكس (Ubuntu / Debian):**
     ```bash
     sudo gpg -k
     sudo gpg --no-default-keyring --keyring /usr/share/keyrings/k6-archive-keyring.gpg --keyserver hkp://keyserver.ubuntu.com:80 --recv-keys C5AD17C747E3415A3642D57D77C6C491D6AC1D69
     echo "deb [signed-by=/usr/share/keyrings/k6-archive-keyring.gpg] https://dl.k6.io/deb stable main" | sudo tee /etc/apt/sources.list.d/k6.list
     sudo apt-get update && sudo apt-get install k6
     ```
   - **ماك (macOS via Homebrew):**
     ```bash
     brew install k6
     ```

2. **التشغيل الفوري:**
   ```bash
   # تشغيل السيناريو الشامل
   npm run test:load

   # أو عبر السكريبت المباشر
   ./load-tests/run.sh scenarios/storefront-checkout.js
   # على ويندوز:
   load-tests\run.bat scenarios\pos-catalog-sync.js
   ```

### الطريقة الثانية: عبر حاوية Docker (بدون تثبيت أي أدوات)

## 3-ب. أحجام الحمل (PROFILE) والتشغيل على الإنتاج

الأحجام معايَرة على مواصفات سيرفر الإنتاج الحالية: **نواتان · 12 جيجا رام · 4 جيجا Swap**،
والباك إند في **عملية واحدة** (PM2 في وضع fork لا cluster — §2.7). عملياً نواة تخدم كل الطلبات
وأخرى لقاعدة البيانات، فالتزاحم يظهر مبكراً وهذا هو المقصود قياسه.

| PROFILE | الذروة | التصاعد | الثبات | الغرض |
|---|---|---|---|---|
| `default` | 50 | 15ث | 30ث | «هل كسرنا حاجة؟» — تشغيل سريع بعد أي تغيير |
| `heavy` | 150 | 30ث | 90ث | حمل ثقيل واقعي مع فرض عتبات الـSLA |
| `extreme` | 300 | 45ث | 120ث | **قياس حدّ السيرفر** — العتبات مُطفأة عمداً |
| `soak` | 40 | 30ث | 600ث | نقع عشر دقائق لكشف تسرّب الذاكرة وتآكل الأداء |

```bash
PROFILE=heavy TARGET_URL=http://127.0.0.1:3000 bash load-tests/run.sh scenarios/stress-all.js
PEAK_VUS=500 HOLD_SECONDS=180 bash load-tests/run.sh   # ضبط يدوي يتجاوز PROFILE
```

**لماذا `extreme` بلا عتبات:** عند 300 مستخدم متزامن على نواتين ستُخرق عتبة الـp95 حتماً،
وk6 يخرج بكود فشل عند خرق أي عتبة — فتبدو النتيجة «فشلاً» بينما هي الرقم المطلوب نفسه.
الملف يطفئها ويطبع الأرقام.

### بيانات الدخول (سيناريوهات الكاشير)

`pos-catalog-sync.js` و`stress-all.js` يحتاجان جلسة حقيقية. الافتراضي في `config.js` هو
`admin/admin` للتطوير المحلي فقط؛ على أي سيرفر حقيقي لا بد من بيانات صحيحة، وإلا **يتوقف
الاختبار فوراً** برسالة صريحة بدل أن يعدّ 401 ويقول «100% فشل».

ضعها في ملف على السيرفر بدل سطر الأوامر — السر لا يدخل سجل الصدفة ولا يظهر في `ps`:

```bash
sudo mkdir -p /etc/zsystems
printf 'AUTH_USERNAME=%s
AUTH_PASSWORD=%s
' 'اسم_المستخدم' 'كلمة_المرور' | sudo tee /etc/zsystems/loadtest.env > /dev/null
sudo chmod 600 /etc/zsystems/loadtest.env && sudo chown "$USER" /etc/zsystems/loadtest.env
```

`run.sh` يقرأه تلقائياً (أو من `CREDENTIALS_FILE=...`).

الجلسة تُحمل في **كوكي**، كما يفعل المتصفح، لا في ترويسة `X-Session-Id`: تلك الترويسة معطَّلة
عمداً في وضع السحابة (`session-auth.guard.ts:allowSessionIdHeaderFallback` — مسموحة في التطوير
والديسكتوب فقط)، وليس على الإنتاج أن يخفّف حمايته ليمر اختبار. واسم الكوكي **لا يُكتب في الكود**:
`SESSION_COOKIE_NAME` مضبوط على هذا النشر، فالسيناريو يكتشفه من ردّ الدخول — الكوكي التي قيمتها
تساوي `sessionId` في الجسم هي كوكي الجلسة أياً كان اسمها. وCSRF لا يُفحص على طلبات القراءة.

### `SPOOF_CLIENT_IPS` — متى ولماذا

حدود المحاولات مفتاحها **عنوان العميل** (O60 للمتجر: 30 طلباً/10 دقائق لكل IP · O72 للدخول).
اختبار يعمل من داخل السيرفر يبدو للتطبيق **عميلاً واحداً**، فبعد الطلب الثلاثين يرد 429 على كل
شيء: الاختبار يقيس الحارس لا قاعدة البيانات، ويطلع أحمر بسبب حماية تعمل صح.

`SPOOF_CLIENT_IPS=true` يعطي كل VU عنواناً مختلفاً في `X-Real-IP`، فيصير 50 مشترياً متزامناً
**خمسين عميلاً فعلاً** لا واحداً. وهذا ليس التفافاً على الحماية: `resolveClientIp` تثق بهذه
الترويسة **فقط** حين يكون القرين عنواناً داخلياً (بروكسي)، و k6 هنا على `127.0.0.1`؛ عميل من
الخارج لا يستطيع فعلها. ومع ذلك تبقى خلف مفتاح صريح حتى لا تُشغَّل بالغلط فتُخفي حدّاً مكسوراً.

**اتركها مطفأة** حين يكون غرضك اختبار الحدود نفسها (`auth-login-burst.js` يريد مهاجماً واحداً).

سيناريوهات **الكتابة** تذهب أبعد: `writerIpHeaders(__VU, __ITER)` تعطي عنواناً جديداً **لكل تكرار**
لا لكل مستخدم. السبب أن حدّ O60 هو 30 طلباً لكل عنوان في 600 ثانية، فجولة بعدد مستخدمين ثابت
تُسقَف عند 30 طلباً لكل VU مهما طالت. والمتجر الحقيقي الذي يستقبل ثمانية آلاف طلب في دقيقتين
يستقبلها من آلاف العناوين لا من مئة وخمسين، فهذه هي **المحاكاة الأصدق** لا التفافاً. وأثر الحدّ
يبقى مرئياً في عدّاد `storefront_rejects_rate_limited`.

### مسار الكتابة: لماذا يلغي الاختبار كل طلب ينشئه

`createOnlineOrder` يتحقق من المخزون **قبل** فتح المعاملة، وكل طلب ناجح **يحجز** مخزوناً
(`reserved_qty`)، والمتاح هو `stock_qty - reserved_qty`. فسيناريو ينشئ الطلبات ولا يلغيها يعمل
بقدر المخزون الفائض فقط، ثم يقضي بقية الجولة يقيس **فرع الرفض** — بلا معاملة واحدة وبلا قفل واحد.
وهذا ما حدث فعلاً في أول جولة إنتاج (24 سبتمبر 2026): نجاح 0.19% وصفر جمود، وقُرئت النتيجة أول
الأمر على أنها صمود بينما كانت عدم اختبار.

فصار السيناريو يلغي كل طلب فور إنشائه (`POST :slug/orders/:orderNumber/cancel` بترويسة
`x-order-token`)، والإلغاء يعيد الحجز عبر `releaseLocationStock` فيبقى الحمل مستمراً بلا سقف.
وهو **زيادة** في الحمل لا نقصان: معاملة ثانية على نفس الأقفال وبنفس الترتيب القانوني، فالضغط على
كاشف الجمود أقوى من قبل.

- `KEEP_ORDERS=true` يعطّل الإلغاء لمن يريد تراكم الطلبات عمداً (اختبار لوحة الطلبات مثلاً)،
  وحينها يطبع `setup()` سقف الجولة المتوقَّع.
- لو لم يجد السيناريو صنفاً واحداً بمخزون متاح **رفض البدء** برسالة صريحة، بدل إخراج نسبة نجاح
  قرب الصفر تُقرأ خطأً على أنها انهيار في السيرفر.
- كل رفض يُصنَّف ويُعدّ: `..._rejects_rate_limited` · `..._rejects_out_of_stock` ·
  `..._rejects_business` · `..._rejects_server`. أول رفضين يُطبع نصّهما في السجل أثناء الجولة.

### ⚠️ قبل التشغيل على الإنتاج

- **`storefront-checkout.js` و`stress-all.js` يُنشئان طلبات حقيقية** في المتجر المستهدف
  (`STOREFRONT_SLUG`): خصم مخزون حقيقي، وصفوف في دفاتر المنشأة، و**رسالة واتساب للمالك لكل طلب**
  إن كانت بوابة واتساب مفعّلة لتلك المنشأة (`whatsapp_gateway_enabled` + `whatsapp_gateway_auto_order`).
  أطفئها من إعدادات المنشأة قبل جولة ثقيلة، أو وجّه الاختبار إلى متجر تجريبي.
- **المخزون:** الطلبات تُلغى تلقائياً فيعود الحجز ولا ينفد المتاح (انظر القسم أعلاه). ومع
  `KEEP_ORDERS=true` ينفد المخزون بعد عدد محدود من الطلبات وتفشل البقية — فشل حقيقي لكنه ليس
  فشل أداء.
- **العنوان الصحيح للإنتاج هو المنفذ 3000** لا 3001 (الافتراضي في `config.js` للتطوير).
- `zsystems-watch.sh` قد يرسل تنبيهاً إن تأخر `health/ready` أثناء الضغط. متوقَّع.
- نظّف بعد الجولة: الطلبات الوهمية تحمل اسم `Shopper VU-…` فيسهل حصرها.

## 5. قراءة وتحليل النتائج ومؤشرات النجاح (SLA Thresholds)

عند اكتمال أي اختبار حمل، تعرض أداة k6 تقريراً إحصائياً دقيقاً. المعايير المعتمدة للمنظومة هي:

1. **`storefront_deadlocks_detected`:** **يجب أن تكون `0` تماماً (count == 0).** أي رقم أكبر من الصفر يعني حدوث خرق للترتيب القانوني للأقفال.
2. **`pos_version_duration_ms`:** **95% من الطلبات أقل من 150ms.** إثبات عمل الـ Trigger السريع وعدم حساب الأرصدة مجدداً.
3. **`pos_full_sync_duration_ms`:** **95% من الطلبات أقل من 600ms** حتى تحت ضغط 50 كاشيراً متزامناً.
4. **`http_req_failed`:** نسبة الأخطاء العامة أقل من 1%.
5. **`login_429_rate_limited_count`:** تأكيد اعتراض المحاولات السريعة وإرجاع كود 429 بعد تجاوز المعدل المسموح.
6. **`storefront_rejects_server`:** **صفر.** خطأ 5xx واحد في مسار كتابة مالي ليس ضجيجاً إحصائياً.
7. **`storefront_order_success_rate`:** فوق 95%. أقل من ذلك يعني أن الجولة قاست فرع الرفض لا
   الكتابة — اقرأ عدّادات `..._rejects_*` قبل أن تلوم السيرفر.

> **تحذير قراءة:** «صفر جمود» لا يعني شيئاً إن كان عدد الطلبات الناجحة صفراً. تحقّق دائماً من
> `storefront_order_success_rate` و`fake_orders` في قاعدة البيانات قبل أن تعلن نجاة مسار الكتابة.

## 7. سيناريو البيع الكامل (`pos-sell.js`)

هذا هو السيناريو الذي كان ناقصاً: كل ما قبله **قراءة**. `POST /api/sales` ليس طلباً واحداً — هو
معاملة تكتب في `sales` و`sale_items`، وتخصم المخزون عبر `applyStockDelta` بالترتيب القانوني
للأقفال، وترحّل قيداً مزدوجاً (وتُنشئ شجرة الحسابات إن لم تكن موجودة — `ensureTenantFoundation`)،
وتحدّث صف الوردية في `cashier_shifts`.

**ثلاث مجموعات تعمل معاً:**

| المجموعة | ماذا تفعل | ماذا تقيس |
|---|---|---|
| `cashiers` | تبيع أصنافاً عشوائية (1–3 أسطر)، و35% منها تُنشئ طلب متجر في نفس اللحظة | الحمل الواقعي: فواتير وقيود ومخزون معاً |
| `hot_product` | تبيع **نفس الصنف** من كل مستخدم | تزاحم صف واحد في `products` وصف واحد في `product_location_stock` — الحمل الموزّع لا يكشف خرق ترتيب الأقفال، هذا يكشفه |
| `health` | مسبار صحة كل 5 ثوانٍ | هل الصندوق ما زال يرد أثناء ذلك |

```bash
# كاشير واحد (وردية واحدة، فتزاحم الكاشير على ورديته هو المقيس)
PROFILE=heavy STOREFRONT_SLUG=<slug> bash load-tests/run.sh scenarios/pos-sell.js

# عدة كاشيرات = عدة ورديات متزامنة فعلاً
CASHIERS='cashier1:pass1,cashier2:pass2,cashier3:pass3' PROFILE=heavy bash load-tests/run.sh scenarios/pos-sell.js
```

| المتغير | الافتراضي | المعنى |
|---|---|---|
| `CASHIERS` | `AUTH_USERNAME:AUTH_PASSWORD` | قائمة `user:pass`. الوردية مفتاحها `opened_by`، أي **مستخدم واحد = وردية واحدة** |
| `HOT_PRODUCT_SHARE` | `0.25` | نصيب الصنف الساخن من الحمل |
| `WITH_STOREFRONT` | `true` | هل يزاحم متسوّقو المتجر الكاشيرات على نفس المخزون |

### ⛔ الفواتير لا تُلغى

البيع حركة حقيقية: يخصم مخزوناً ويرحّل قيداً، **والقيد المزدوج غير قابل للحذف بحكم ثابت معماري**.
جولة واحدة تكتب آلاف الفواتير وقيودها في دفاتر المنشأة المستهدفة إلى الأبد.

**لا تشغّل هذا على منشأة حقيقية.** استخدم منشأة اختبار بمخزون وفير — لأن المخزون هنا **يُستهلك**
ولا يعود (بخلاف `storefront-checkout.js` الذي يلغي طلباته فيعيد الحجز).

### ما يوقف الجولة قبل أن تبدأ

نفس مبدأ §6-د: `setup()` يسجّل الدخول، ويفتح وردية لكل كاشير، **ويصدر فاتورة تجريبية واحدة**.
إن رفض السيرفر أياً من الثلاثة توقف الاختبار فوراً برسالة السيرفر. ويستبعد `setup()` الأصناف التي
تفشل لأسباب ليست أداءً: الخدمات والمواد الخام، والأصناف بأرقام تسلسلية، والتجميعات (BOM).

### العدّادات التي تُقرأ

- `sale_success_rate` و`hot_product_sale_success_rate` — الثاني عتبته أدنى (0.90) لأن التزاحم مقصود.
- `sell_deadlocks_detected` — **صفر**. وهذه المرة الصفر يعني شيئاً، لأن الفواتير تُكتب فعلاً.
- `sell_rejects_no_open_shift` — لو قفز، فالورديات لم تُفتح والجولة تقيس التفويض لا الأداء.
- `sell_units_sold` — كم وحدة خرجت من المخزون فعلاً.

## 6. خط الأساس المقيس على الإنتاج (24 سبتمبر 2026)

سيرفر Oracle ARM واحد: نواتان · 12 جيجا رام · 4 جيجا سواب · PM2 في وضع fork (عملية واحدة) ·
k6 يعمل على **نفس الصندوق** ويضرب `127.0.0.1:3000` مباشرة.

### 6-أ. ماذا أرسل كل سيناريو بالضبط

الأسماء مختصرة ومضلِّلة إن قُرئت على ظاهرها، فهذا ما يرسله كل واحد فعلاً:

| السيناريو | الطلبات التي يرسلها | ما لا يرسله |
|---|---|---|
| `pos-catalog-sync.js` | `GET /api/catalog/pos-products/version` كل تكرار، و`GET /api/catalog/pos-products?limit=200` في 30% من التكرارات | **لا بيعة واحدة.** لا فاتورة، لا قيد، لا حركة مخزون |
| `auth-login-burst.js` | `POST /api/auth/login` بكلمة مرور **خاطئة**، 30 محاولة/ث من **عنوان واحد** | لا يختبر نجاح الدخول ولا الجلسات |
| `storefront-checkout.js` | `GET catalog` ثم `POST :slug/orders` ثم `POST :slug/orders/:num/cancel` | لا يحوّل الطلب إلى فاتورة، ولا يمرّ على الكاشير |
| `stress-all.js` | الثلاثة معاً: فحص نسخة الكاشير + طلب متجر + `GET /health` | نفس النواقص أعلاه مجتمعة |

> «150 كاشيراً» تعني **150 شاشة كاشير مفتوحة** تسأل كل ثانية ونصف «هل تغيّرت قائمة الأصناف؟»،
> لا 150 كاشيراً يبيعون. الفرق جوهري: الأولى قراءة، والثانية معاملة تكتب في `sales` و`sale_items`
> و`journal_entries` و`product_location_stock` معاً.

### 6-ب. الأرقام المقيسة

| الجولة | الحمل | النتيجة |
|---|---|---|
| مزامنة الكاشير (قراءة) | 150 مستخدماً · 135ث · 80 طلباً/ث | `p(95)=6.54ms` · `p(99)=9.87ms` · صفر فشل · 10,822 طلباً |
| انفجار الدخول (مهاجم واحد) | 30 محاولة/ث · 20ث | 501 من 601 رُدّت بـ429 — الحدّ يعمل · `p(95)=9ms` |
| الضغط الأقصى المشترك | 600 مستخدماً · 189ث · 297 طلباً/ث | `p(95)=34.18ms` · 56,251 طلباً · فحص الصحة 100% سليم |
| بعد العاصفة | — | `health/ready` = 200 في **2.5ms** · صفر جمود · **صفر سواب** · الذاكرة 1.2 من 11 جيجا |

`load average` بلغ **2.45 على نواتين** في ذروة الجولة الرابعة — أي أن المعالج كان مشبعاً بالفعل،
ومع ذلك بقي `p(95)` عند 34ms. هذا هو الرقم المفيد من الجولة: السيرفر يشبع ولا ينهار.

### 6-ج. ما اختُبر وما لم يُختبر

هذه الجولة اختبرت **السيرفر**، لا **النظام**. الفرق ليس لفظياً:

| ✅ اختُبر فعلاً | ❌ لم يُختبر إطلاقاً |
|---|---|
| قدرة الصندوق على خدمة مئات القرّاء المتزامنين | **البيع نفسه** — لا سيناريو ينادي مسار إصدار الفاتورة. صفر فاتورة |
| مسار `pos-products/version` السريع (PERF-9) | القيود المحاسبية المزدوجة تحت ضغط |
| حدّ محاولات الدخول (O72) حيّاً على الإنتاج | حركة المخزون الناتجة عن بيعة |
| ثبات الذاكرة: صفر سواب عند الإشباع | الورديات والخزينة والعُهد |
| مسبار الصحة تحت الإشباع | المشتريات والمرتجعات والتحويلات |
| صمود العملية الواحدة (لا إعادة تشغيل واحدة) | التقارير تحت ضغط |
| | **كاشيران يبيعان نفس الصنف في نفس اللحظة** — وهو أخطر تزاحم في المنظومة |
| | إنشاء طلب المتجر (ارتدّ قبل المعاملة — انظر 6-د) |

وثلاثة قيود على بيئة القياس نفسها:

- **الاختبار تجاوز nginx:** ضرب `127.0.0.1:3000` مباشرة. فلا TLS ولا تخزين مؤقت في nginx ولا زمن
  شبكة حقيقي داخل هذه الأرقام. المستخدم الحقيقي يدفع كل ذلك فوقها.
- **كتالوج الكاشير لهذه المنشأة فارغ** (`totalCount: 0`)، فجولة القراءة قاست المسار لا البيانات.
  كتالوج فيه عشرة آلاف صنف رقم آخر تماماً.
- **منشأة واحدة فقط.** لا قياس لتزاحم عدة مستأجرين على نفس القاعدة.

### 6-د. الدرس: «صفر جمود» قد يعني «صفر محاولات»

جولة الشراء أعادت `نجاح 0.19% — 16 من 8249` و`صفر جمود`، وقُرئت أول الأمر على أنها صمود.
لم تكن: `createOnlineOrder` يتحقق من المخزون **قبل** فتح المعاملة، وكل طلب ناجح يحجز مخزوناً،
فبعد 16 طلباً نفد المتاح وارتدّت البقية من الباب بلا معاملة ولا قفل. و`xact_rollback` في قاعدة
البيانات (1584 لا 8233) أكّد ذلك.

**فلا يُقرأ أي عدّاد جمود قبل التأكد من عدد المحاولات الناجحة.**

والجولة الثانية (بعد إصلاح المخزون) أعادت `0.00% — 0 من 8225`، لكنها هذه المرة **قالت السبب في
ثلاث ثوانٍ** بدل أن يُستنتج بعد ساعة: «الحد الأدنى للطلب هو 700 ج». السلة كانت قطعة واحدة دائماً،
والمتجر يرفض أي سلة تحت 700. التصنيف نجح، لكن الدقيقتين والنصف ضاعتا.

فأُضيف شيئان أخيران:

1. **السلة تُبنى لتتجاوز الحد الأدنى** المقروء من `GET :slug/info`، بكمية محسوبة لكل صنف
   (`selectOrderableItems` في `config.js`)، وتُفضَّل الأصناف الأغلى لأن كميتها أصغر فتستهلك
   مخزوناً أقل.
2. **طلب تجريبي واحد في `setup()`** يُنشأ ويُلغى قبل أن يبدأ الحمل. إن رفضه السيرفر توقف الاختبار
   فوراً **برسالة السيرفر نفسها**. جولة كاملة بلا معنى صارت مستحيلة بنيوياً، لا مجرد غير محتملة.

خط أساس الكتابة ما زال **غير مقيس** — البند O74 في `ARCHITECTURE_INVARIANTS.md`.

### 6-هـ. الخلاصة الصادقة

السيرفر عنده فائض سعة واضح للقراءة: أشبع نواتيه عند 600 مستخدم متزامن وظل يرد في 34ms بلا سواب
وبلا إعادة تشغيل. أما **جاهزية النظام للبيع الفعلي فلم تُقَس بهذه الجولة** — البيع لم يُنادَ ولا
مرة. الخطوة التالية سيناريو يبيع فعلاً: إصدار فاتورة، وقيدها المحاسبي، وحركة مخزونها، وكاشيران
على نفس الصنف.
